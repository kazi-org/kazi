Code anchors verified on origin/main at triage time (2026-09-02):
`Kazi.Enforcement.Isolation.prepare/3` (lib/kazi/enforcement/isolation.ex:
81-96) creates the checker's clean-tree worktree via `git worktree add
--detach <tmp> <ref>` (line 85) -- ALWAYS detached, because the goal's real
branch is simultaneously checked out in the primary workspace and git
refuses the same branch checked out in two worktrees at once (this is by
design, not a bug -- see the module's own moduledoc). `Kazi.Loop.
observe_with_isolation/1` (loop.ex:1656-1671) routes only `isolated?/1`
predicates (`Predicate.guard?/1` or `Predicate.held_out?/1`, ADR-0042 SS1/SS6
anti-gaming enforcement) into that detached worktree; ordinary iterating
predicates keep running against the real workspace (`ws`), where `@{u}` and
`--abbrev-ref HEAD` resolve fine. `Kazi.Goal.integration_branch/1`
(lib/kazi/goal.ex, T54.1/#1079) already computes the goal's real target
branch name deterministically and is the established precedent for
threading branch identity into run-time context (it already solved the
sibling "the scheduler's synthetic branch isn't the branch a `landed`
predicate names" problem in E54).

Acceptance: #1709 closed citing a merged PR; the fix is proven by a
red-to-green replay of the exact repro in the issue (a `custom_script` guard
predicate reading `git rev-parse '@{u}'` or comparing `--abbrev-ref HEAD` to
the goal's real branch, converged work already committed and pushed);
neither of the two confirmed repro shapes in the issue (the `@{u}`
resolution failure, and the direct `--abbrev-ref HEAD` branch-name-equality
failure) regresses; the fix does not weaken clean-tree isolation for any
other predicate class; docs land with the code (ADR-0034).

## Tasks

- [ ] T71.1 Fix #1709 -- guard/held-out predicates that assert branch
  identity or upstream tracking are structurally unsatisfiable inside the
  isolation worktree, because `Isolation.prepare/3` always creates it
  `--detach`ed (confirmed: `--abbrev-ref HEAD` returns the literal string
  `HEAD` there, and `git rev-parse '@{u}'` fatals with no
  `branch.<name>.remote` config to resolve, regardless of which commit the
  worktree was created from). Two confirmed repro variants in the issue:
  (a) `test "$(git rev-parse HEAD)" = "$(git rev-parse '@{u}' 2>/dev/null)"`
  degrades silently to comparing against an empty string when the fatal is
  swallowed (`2>/dev/null`), reporting exit 1 with an empty `output` field
  and no hint of the real cause; (b) a direct
  `[ "$(git rev-parse --abbrev-ref HEAD)" = 'task/<goal-branch>' ]` check
  fails identically, on every iteration, on every goal, independent of
  `@{u}`. Both variants only affect a predicate that ran isolated (guard or
  held-out) -- the reporter confirmed every non-isolated capability
  predicate for the same goal converged normally in the same run. Fix
  primary direction (per the issue's own suggested fix 1, and the T54.1
  precedent that already computes this value): thread the goal's real
  target branch -- `Kazi.Goal.integration_branch/1` -- into the isolated
  worktree's predicate-execution environment as `KAZI_GOAL_BRANCH` (and, if
  an `origin` remote is configured in the base workspace, an
  `KAZI_GOAL_UPSTREAM` set to `origin/<branch>` so a predicate can compare
  `HEAD` against a real resolvable ref instead of the structurally-broken
  `@{u}`); this does not require setting a real git upstream on the
  detached worktree, which the issue itself rules out as impossible (git
  refuses the same branch checked out twice). Wire the injection at the
  `observe_with_isolation/1` call site (or lower, in
  `Isolation.with_clean_tree/4`/`prepare/3`) so it reaches whichever
  provider (`custom_script`, `test_runner`) actually spawns the subprocess,
  alongside any goal-file-declared `env` (custom_script.ex's existing
  `normalize_env/1` env-merge, ~line 509) rather than replacing it.
  Secondary, doc-only mitigation regardless of the primary fix: add a
  predicate-authoring guide note (AUTHORING.md, alongside the T70.7 lint
  hazards it is the same family as -- "a shell/git idiom that silently
  interacts badly with kazi's execution environment") stating plainly that
  a predicate reachable by clean-tree isolation runs in a DETACHED worktree
  with no branch identity of its own, and that `@{u}`/`--abbrev-ref
  HEAD`/`git status -sb` ahead-behind parsing are unstable there --
  `$KAZI_GOAL_BRANCH`/`$KAZI_GOAL_UPSTREAM` (once shipped) or an explicit
  remote-tracking-ref comparison are the stable alternative. If a `kazi
  lint` static check for these patterns already exists after T70.7 lands,
  extend it to also flag `@{u}`/`--abbrev-ref HEAD` inside a predicate
  known to be guard/held-out (no hard dependency -- land independently,
  reconcile authorship of the shared lint feature at merge time if both
  land close together).  Owner: pool  Est: 3.5h  kind: agent
  verifies: [infrastructure]  deps: []
